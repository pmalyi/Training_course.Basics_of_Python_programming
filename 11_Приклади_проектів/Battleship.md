## Гра «Морський бій» (Battleship) — реалізація на Python з використанням ООП

### Мета заняття

- Використання класів та об'єктно-орієнтованого підходу в Python
- Реалізація простої ігрової логіки
- Робота зі списками (`list`)
- Використання переліків (`enum.Enum`) для представлення напрямку

---

## 1. Підготовка

За основу необхідно взяти структуру проєкту, що складається з п'яти класів (див. розділ 2). Дозволяється довільно розширювати класи, тобто додавати до них **будь-яку кількість власних (приватних) атрибутів і методів**, необхідних для реалізації внутрішньої логіки.

**Забороняється:**
- видаляти чи змінювати сигнатури атрибутів і методів, що описані в цьому завданні як публічні;
- перейменовувати публічні методи/атрибути або додавати нові публічні методи/атрибути замість описаних.

Коротко: **усе, що є публічним інтерфейсом класу, повинно залишатися незмінним.**

Усі приватні атрибути в Python позначаються через префікс з одним підкресленням (`_row`, `_status` тощо) — це є прийнятою угодою (convention) для позначення "приватності" в мові Python, оскільки справжньої мовної інкапсуляції там немає.

---

## 2. Гра «Морський бій» (Battleship)

Гра розрахована на двох гравців, які в реальних умовах не повинні бачити ігрове поле один одного. У цій реалізації поля обох гравців виводяться в одну й ту саму консоль почергово (мета завдання — не створення ідеальної гри, а відпрацювання об'єктно-орієнтованої логіки програмування).

Кожен гравець розміщує на полі 10×10 клітинок загалом десять кораблів різної довжини (від двох до п'яти клітинок). Гравець-суперник «обстрілює» поле, вказуючи рядок і стовпець клітинки. У відповідь гравець повідомляє або «Вода», якщо жоден корабель не влучено, або «Влучання», якщо корабель уражено.

Крім основного поля, кожен гравець зазвичай має додатковий «журнал пострілів» (cheat sheet), на якому позначається, які клітинки поля суперника вже було обстріляно.

Для реалізації гри проєктуються **п'ять класів**:

| Клас | Призначення |
|---|---|
| `Player` | представляє гравця, зберігає ім'я та кількість виграних/програних ігор |
| `Part` | представляє одну частину корабля, що займає рівно одну клітинку поля |
| `Ship` | представляє корабель, що складається з декількох об'єктів `Part` |
| `GameBoard` | зберігає кораблі гравця та «журнал пострілів», відповідає за виведення поля |
| `Battleship` | головний клас гри, керує двома об'єктами `Player` та відповідними `GameBoard` |

## 3. Схема класів

### 3.1 Клас `Player`

Клас відповідає за зберігання інформації про одного гравця: ім'я, кількість виграних і програних ігор.

**Атрибути (приватні):**

| Атрибут | Тип | Опис |
|---|---|---|
| `_player_name` | `str` | Ім'я гравця (незмінне після створення) |
| `_games_won` | `int` | Кількість виграних ігор |
| `_games_lost` | `int` | Кількість програних ігор |

**Методи (публічні):**

| Метод | Сигнатура | Опис |
|---|---|---|
| Конструктор | `__init__(self, player_name: str)` | Ініціалізує `_player_name` переданим значенням, `_games_won` та `_games_lost` — нулями |
| `get_games_won` | `() -> int` | Повертає кількість виграних ігор |
| `get_games_lost` | `() -> int` | Повертає кількість програних ігор |
| `get_games_played` | `() -> int` | Повертає загальну кількість зіграних ігор (сума виграних і програних) |
| `add_game_won` | `() -> None` | Збільшує кількість виграних ігор на 1 |
| `add_game_lost` | `() -> None` | Збільшує кількість програних ігор на 1 |
| `get_name` | `() -> str` | Повертає ім'я гравця |

> **Примітка:** атрибут `_player_name` за змістом є незмінним (константним) — після встановлення в конструкторі він не повинен більше змінюватися жодним публічним методом.

---

### 3.2 Клас `Part`

Клас представляє одну частину корабля, яка займає рівно одну клітинку ігрового поля. Об'єкт `Part` «знає» власну позицію на полі, але **не знає**, якому кораблю належить і чи затонув цей корабель.

**Атрибути (приватні):**

| Атрибут | Тип | Опис |
|---|---|---|
| `_row` | `int` | Рядок, у якому розташована частина корабля |
| `_col` | `int` | Стовпець, у якому розташована частина корабля |
| `_status` | `int` (або `bool`) | Стан частини: `0`/`False` — не пошкоджена, `1`/`True` — пошкоджена |

**Методи (публічні):**

| Метод | Сигнатура | Опис |
|---|---|---|
| Конструктор | `__init__(self, row: int, col: int)` | Створює непошкоджену частину корабля в заданій позиції; `_status` ініціалізується значенням «не пошкоджено» |
| `is_damaged` | `() -> bool` | Повертає `True`, якщо частину пошкоджено |
| `set_damaged` | `() -> None` | Встановлює статус частини як «пошкоджено». Зворотної дії («ремонт») не передбачено |
| `get_row` | `() -> int` | Повертає рядок розташування частини |
| `get_col` | `() -> int` | Повертає стовпець розташування частини |

---

### 3.3 Клас `Ship`

Клас представляє корабель, що складається зі списку об'єктів `Part`. Сам об'єкт `Ship` не зберігає власну позицію — позиції зберігаються окремо, у кожному об'єкті `Part`.

Оскільки кораблі мають різну кількість частин, для їх зберігання використовується звичайний Python-список (`list`).

Напрямок розташування корабля представляється переліком:

```python
from enum import Enum

class Direction(Enum):
    NORTH = 0  # вгору
    EAST = 1   # праворуч
    SOUTH = 2  # вниз
    WEST = 3   # ліворуч
```

**Атрибути (приватні):**

| Атрибут | Тип | Опис |
|---|---|---|
| `_parts` | `list[Part]` | Список частин, з яких складається корабель |

**Методи (публічні):**

| Метод | Сигнатура | Опис |
|---|---|---|
| Конструктор (порожній) | `__init__(self)` | Створює «порожній» корабель без частин. Потрібен для того, щоб можна було заздалегідь створити список/масив кораблів у `GameBoard`, а потім заповнити їх фактичними кораблями |
| `build` (або перевантажений конструктор через параметри за замовчуванням) | `(self, row: int, col: int, length_of_ship: int, direction: Direction)` | Формує корабель довжиною `length_of_ship`, перша частина якого розташована в `(row, col)`. Наступні частини розміщуються в напрямку `direction` |
| `has_part_in` | `(row: int, col: int) -> bool` | Повертає `True`, якщо частина цього корабля розташована в заданій клітинці |
| `get_part_in` | `(row: int, col: int) -> Part` | Повертає посилання (об'єкт) на частину корабля в заданій клітинці. Якщо такої частини немає — можна викликати виключення `ValueError` (аналог `std::invalid_argument`) або вважати, що вхідні дані завжди коректні |
| `is_damaged` | `() -> bool` | Повертає `True`, якщо пошкоджена хоча б одна частина корабля |
| `is_sunk` | `() -> bool` | Повертає `True`, якщо пошкоджені всі частини корабля (корабель затонув) |

**Логіка побудови корабля:** перша частина завжди створюється в позиції `(row, col)`. Далі, залежно від `direction`, кожна наступна частина зсувається на одну клітинку відносно попередньої:
- `NORTH` → рядок зменшується (`row - 1`)
- `SOUTH` → рядок збільшується (`row + 1`)
- `EAST` → стовпець збільшується (`col + 1`)
- `WEST` → стовпець зменшується (`col - 1`)

Наприклад, для `row=3`, `col=2`, `length_of_ship=3`, `direction=EAST` створюються частини на позиціях `(3,2)`, `(3,3)`, `(3,4)`.

### 3.4 Клас `GameBoard`

Клас надає перелік кораблів одного гравця (список із 10 об'єктів `Ship`), а також керує «журналом пострілів» — двовимірним списком розміром 10×10 символів, у якому позначається, по яких клітинках поля суперника вже стріляв цей гравець.

**Атрибути (приватні):**

| Атрибут | Тип | Опис |
|---|---|---|
| `_ships` | `list[Ship]` (10 елементів) | Кораблі гравця |
| `_enemy_board` | `list[list[str]]` (10×10) | «Журнал пострілів»: позначки про постріли по полю суперника |

**Методи (публічні):**

| Метод | Сигнатура | Опис |
|---|---|---|
| Конструктор | `__init__(self, place_ships: bool = False)` | Заповнює `_enemy_board` символом «ще не стріляли» (наприклад `'.'`). За бажанням одразу викликає `random_place_ships()` |
| `print_board` | `() -> None` | Виводить власне поле гравця в консоль |
| `print_enemy_board` | `() -> None` | Виводить «журнал пострілів» гравця в консоль |
| `hit` | `(row: int, col: int) -> bool` | Обробляє постріл суперника по клітинці `(row, col)`: якщо там є частина корабля — позначає її пошкодженою й повертає `True`, інакше повертає `False` |
| `mark` | `(row: int, col: int, was_hit: bool) -> None` | Позначає в `_enemy_board`, що клітинку `(row, col)` вже обстріляно: `'X'`, якщо влучання, або `'O'`, якщо повз |
| `random_place_ships` | `() -> None` | Випадковим чином розміщує на полі всі 10 кораблів (див. нижче), заповнюючи `_ships`. Кожен виклик повинен генерувати нове (інше) розташування |
| `all_ships_sunk` | `() -> bool` | Повертає `True`, якщо всі кораблі гравця затонули |

**Символи для виведення власного поля (`print_board`):**

| Стан клітинки | Позначення |
|---|---|
| Вода (немає корабля) | `.` |
| Непошкоджена частина корабля | номер корабля (індекс у списку `_ships`) |
| Пошкоджена частина корабля (сам корабель ще не затонув) | `X` |
| Частина затонулого корабля | `S` (або `#`) |

**Символи для «журналу пострілів» (`print_enemy_board`):**

| Стан клітинки | Позначення |
|---|---|
| Постріл ще не робився | `.` |
| Влучання в цю клітинку | `X` |
| Промах (вода) у цій клітинці | `O` |

**Метод `random_place_ships()` повинен розмістити:**

- 1 «Лінкор» (Dreadnought) — 5 частин
- 2 «Крейсери» (Cruiser) — 4 частини кожен
- 3 «Есмінці» (Destroyer) — 3 частини кожен
- 4 «Підводні човни» (Submarine) — 2 частини кожен

Кораблі не повинні перетинатися між собою, а всі їхні частини повинні знаходитися в межах поля 10×10. Кожен виклик методу повинен реально генерувати нове розташування — зокрема, обидва гравці на старті гри повинні отримувати різні розташування кораблів.

### 3.5 Клас `Battleship`

Головний клас гри, що керує двома об'єктами `Player` та відповідними їм об'єктами `GameBoard`.

**Атрибути (приватні):**

| Атрибут | Тип | Опис |
|---|---|---|
| `_players` | `list[Player]` (2 елементи) | Обидва гравці |
| `_boards` | `list[GameBoard]` (2 елементи) | Ігрові поля, що відповідають гравцям |

**Методи (публічні):**

| Метод | Сигнатура | Опис |
|---|---|---|
| Конструктор | `__init__(self, player1_name: str, player2_name: str)` | Створює та ініціалізує обидва об'єкти `Player` за переданими іменами |
| `play` | `() -> None` | Запускає один раунд гри (див. алгоритм нижче) |

**Алгоритм методу `play()`:**

1. Створити для обох гравців нові об'єкти `GameBoard` (кораблі розставляються випадково, журнали пострілів — порожні), замінивши ними попередні значення в `_boards`.
2. Визначити активного гравця (випадковим жеребкуванням або завжди першим гравцем).
3. У циклі, поки жоден гравець не програв:
   1. Вивести на консоль поле та журнал пострілів активного гравця.
   2. Запитати в активного гравця координати клітинки для пострілу по супернику.
   3. Викликати `hit(row, col)` на полі **неактивного** гравця.
   4. Повідомити активному гравцю результат пострілу та відповідно оновити його журнал пострілів методом `mark`.
   5. Поміняти гравців місцями (активний стає неактивним і навпаки).
4. Гра завершується, коли всі кораблі одного з гравців затонули (`all_ships_sunk() == True`). Переможцю викликати `add_game_won()`, переможеному — `add_game_lost()`.

## 4. Вимоги до реалізації (консольний інтерфейс)

1. Реалізувати проєкт мовою Python з використанням об'єктно-орієнтованого підходу, дотримуючись описаної вище схеми п'яти класів.
2. Кожен клас розмістити в окремому файлі (`player.py`, `part.py`, `ship.py`, `game_board.py`, `battleship.py`), а точку входу — у файлі `main.py`.
3. Усі докстрінги та пояснювальні коментарі в коді — українською мовою. Назви класів, методів і атрибутів — англійською.
4. Приватні атрибути позначати одним підкресленням (`_attribute`); доступ до них — лише через описані публічні методи (гетери/сетери).
5. Гра має запускатися й повністю проходити через консоль: введення координат пострілу здійснюється через `input()`, виведення поля та результатів — через `print()`.
6. Передбачити перевірку коректності введених гравцем координат (число в діапазоні 0–9, клітинка ще не обстрілювалася).
7. Для випадкового розміщення кораблів використати модуль `random` стандартної бібліотеки.
8. Продемонструвати роботу програми: провести повний ігровий раунд між двома гравцями (імена вводяться на старті) до перемоги одного з них, з коректним оновленням статистики `_games_won` / `_games_lost`.

## 5. Додаткова вимога: графічний інтерфейс (GUI)

Останнім етапом виконання завдання необхідно реалізувати цей проєкт **із використанням графічного інтерфейсу користувача (GUI)**, зберігаючи ту саму об'єктно-орієнтовану модель класів (`Player`, `Part`, `Ship`, `GameBoard`, `Battleship`) — тобто GUI-версія має лише додавати новий рівень візуалізації та взаємодії, не змінюючи публічний інтерфейс ігрової логіки.

**Рекомендований інструментарій:** бібліотека `tkinter` (входить до стандартної бібліотеки Python) або, за бажанням, `PyQt`/`PySide`.

**Яким має бути графічний інтерфейс:**

- **Ігрове поле у вигляді сітки кнопок або клітинок** 10×10 для кожного гравця, з можливістю клацнути по клітинці поля суперника, щоб здійснити постріл.
- **Візуальне розрізнення станів клітинок** кольором або іконкою: вода, непошкоджений корабель (лише для власного поля), влучання, промах, затонулий корабель — замість символьного виведення в консоль.
- **Окрема панель або вкладка** для «журналу пострілів» (яка повторює логіку `print_enemy_board`, але у графічному вигляді).
- **Індикація поточного активного гравця** (наприклад, підпис або підсвітка) та повідомлення про результат останнього пострілу («Влучання!» / «Вода»).
- **Екран/вікно завершення гри** з оголошенням переможця та відображенням оновленої статистики (`get_games_won`, `get_games_lost`, `get_games_played`) обох гравців.
- **Форма для введення імен гравців** та кнопка «Нова гра» / «Почати заново», яка запускає `Battleship.play()` заново з новими ігровими полями.
- Бажано **приховувати корабель супротивника** — тобто під час гри показувати гравцю лише журнал пострілів по чужому полю, а не саме поле суперника з розташуванням кораблів (це наближає гру до її класичних правил, на відміну від консольної версії, де поля виводились в одну консоль).

Реалізація GUI не повинна дублювати ігрову логіку — усі правила (влучання, розміщення кораблів, визначення переможця) залишаються інкапсульованими в класах `Ship`, `GameBoard` та `Battleship`; графічний шар лише викликає їхні публічні методи та відображає результат.
